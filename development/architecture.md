# 架构与实现边界

## 按设计文档执行的决策

- Flutter 3.x 负责 Android 外壳、消息流、相机、缓存和推送；H5 通过 WebView 承载可复用页面。当前只建立两端入口，WebView 与桥接尚未接线。
- Python 3.11 + FastAPI 作为唯一业务入口，微信轻量触点后续复用同一应用服务。
- 智能层分别封装 LLM、嵌入、混合检索、重排和视觉提供方。开发用 Chroma，生产 Milvus；尚未引入这些依赖，避免将选型占位误认为已完成集成。
- 提醒采用时间轴配置 + APScheduler + 推送队列，推送供应商在设备到达率验证后确定。
- 数据分析后置；不记录原始提问、截图或个人身份信息。

## 核心调用顺序

`HTTP 校验 → 意图/澄清 → 查询改写 → 官方层混合检索 → 重排 → 相关度闸门 → 受限生成 → 字段与出处校验 → 卡片/带出处文本/拒答`

经验层只能补充，不能独立支撑办理资格、材料、地点和期限判断。模型输出的来源必须映射到真实检索片段，不能直接信任生成的来源名称。

## 文档中的歧义处理

1. 拒答在优先级矩阵中为 P1，在附录 F-04 为 P0：按 P0 执行，第一条链路即具备拒答。
2. 官方层无结果可查经验层，但经验层不能作为唯一依据：只给标明非官方的补充或咨询引导，不生成正式办理卡片。
3. 截止日期早于当前日期：保留真实日期并标注过期，不能改为未来日期。
4. 服务故障时只有存在已验证出处才降级为文本；没有依据时说明暂无法核实，不能为满足“有答案”编造内容。
5. 示例中的地点、期限和材料不是学校真实数据，不得直接入正式知识库。

## 首轮完成条件

一份真实公开且经人工核实的学校文档，支持单事项提问、依据片段定位、出处回链和卡片展示；未知问题拒答。完成后才扩大到 ≥15 个具体事项（六大类不是十五个事项）。

技术指标均是后续验收目标：准确率 ≥85%、出处正确率 100%、拒答正确率 ≥95%、平均响应 ≤3 秒、Top-5 召回 ≥90%。200 QPS 与 2核4G 起步部署需分别实测，当前不做容量承诺。
