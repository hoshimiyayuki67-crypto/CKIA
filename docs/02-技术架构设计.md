# 02 技术架构设计

## 一、总体架构

系统采用 **客户端 — 接入层 — 应用层 — 智能层 — 数据层** 架构，其中安卓 APP 与微信端作为并列客户端，共用同一套后端处理链路。

```
┌───────────────────────────┐   ┌───────────────────────────┐
│ 安卓 APP（Kotlin+Compose）│   │ 微信公众号 / 企业微信      │
│  聊天 · 办事卡片 · 截图    │   │  XML 消息                  │
└─────────────┬─────────────┘   └─────────────┬─────────────┘
              │ JSON REST                     │ XML
              └───────────────┬───────────────┘
                              ▼
┌────────────────────────────────────────────┐
│ 接入层：/api/v1（安卓）· /wechat（微信）     │
│  消息接收 · 消息下发 · 卡片渲染              │
└───────────────────┬────────────────────────┘
                    ▼
┌────────────────────────────────────────────┐
│ 应用层（Python 3.11 + FastAPI）             │
│  会话管理 · 意图识别 · 多模态分发            │
│  字段抽取 · 卡片组装 · 定时调度              │
│  反馈收集 · 数据埋点                        │
└───────────────────┬────────────────────────┘
                    ▼
┌────────────────────────────────────────────┐
│ 智能层                                      │
│  大语言模型（理解与生成）                    │
│  嵌入模型（向量化）· 重排模型（相关性排序）  │
│  视觉模型（截图理解）                        │
└───────────────────┬────────────────────────┘
                    ▼
┌────────────────────────────────────────────┐
│ 数据层                                      │
│  向量库（知识索引）· 文档库（原文）          │
│  会话日志（匿名）· 时间轴配置库              │
└────────────────────────────────────────────┘
```

## 二、技术选型

| 层次 | 技术方案 | 选型理由 |
| --- | --- | --- |
| 客户端 | Kotlin + Jetpack Compose（安卓 APK） | 原生体验，构建标准 APK，便于参赛交付 |
| 客户端网络 | Retrofit + OkHttp + Gson | 与后端 JSON REST 对接，成熟稳定 |
| 接入（备用） | 微信公众号 / 企业微信 | 零安装成本，可作为第二入口 |
| 后端框架 | Python 3.11 + FastAPI | 异步性能好，与大模型生态契合 |
| 大语言模型 | DeepSeek / 通义千问 API | 中文能力强、国内直连、成本可控 |
| 嵌入模型 | BGE 系列中文嵌入模型 | 中文语义检索效果好，开源可本地部署 |
| 向量数据库 | Chroma（开发）/ Milvus（生产） | 轻量起步，可平滑扩展 |
| 视觉模型 | Qwen-VL / GLM-4V | 中英文图文理解，支持表格与版面 |
| 定时调度 | APScheduler | 轻量，适合学期时间轴任务 |
| 文档解析 | PyMuPDF + python-docx | 覆盖 PDF 与 Word 格式的校内文档 |
| 部署 | 云服务器（2核4G 起） | 支持私有化部署，满足校方数据要求 |

## 三、核心技术方案

### 1. RAG 检索增强生成链路

**设计目标**：让模型的每一句回答都有据可查。

| 环节 | 做法 | 要点 |
| --- | --- | --- |
| 文档切分 | 按语义段落切分，保留标题层级 | 避免切断完整条款 |
| 元数据附加 | 每段附加文件名、部门、日期、事务类别 | 支撑出处标注与过滤检索 |
| 向量化 | 嵌入模型生成向量，写入向量库 | 采用归一化向量，余弦相似度检索 |
| 混合检索 | 向量检索 + BM25 关键词检索 | 兼顾语义匹配与专有名词精确匹配 |
| 重排序 | 重排模型对候选片段二次排序 | 提升 Top-K 精度 |
| 阈值判定 | 相关度低于阈值即拒答 | 幻觉控制的关键闸门 |
| 生成约束 | 提示词限定"仅依据给定材料作答" | 从输入侧压缩自由发挥空间 |
| 出处绑定 | 生成时同步输出引用的片段编号 | 实现答案与来源的一一对应 |

**链路伪代码**（对应 [app/intelligence/rag.py](../app/intelligence/rag.py)）：

```python
def answer(question: str, img=None) -> Card | Refusal:
    intent = classify_intent(question)          # 意图识别
    query  = rewrite(question)                  # 查询改写
    hits   = hybrid_search(query, intent)       # 混合检索
    hits   = rerank(hits)                       # 重排序
    if top_score(hits) < THRESHOLD:             # 相关度闸门
        return refusal(intent)                  # 拒答并给出咨询渠道
    draft = llm_generate(question, context=hits)  # 受限生成
    fields = extract_fields(draft, hits)        # 字段抽取
    fields = validate(fields)                   # 字段校验
    return build_card(fields, sources=hits)     # 卡片组装
```

### 2. 多模态截图理解方案

**双通道并行**：

| 通道 | 处理内容 | 用途 |
| --- | --- | --- |
| 文本通道 | OCR 提取文字，保留阅读顺序 | 精确获取条款内容与数字 |
| 视觉通道 | 模型直接理解版面：标题、表格、落款、公章 | 判断文件性质与发布主体 |

**融合判定**：

1. 两通道结果一致性校验，不一致时以视觉通道判断的版面归属为准；
2. 提取关键标识（文件名、发布部门、日期）与知识库比对；
3. 若匹配成功，按知识库正式版本回答，并提示"与现行文件一致"；
4. 若匹配失败或存在版本差异，提示用户核实并给出咨询渠道。

对应实现：[app/core/multimodal.py](../app/core/multimodal.py)。

### 3. 结构化输出与卡片生成

**三段式约束**：

1. **格式约束**：提示词要求模型以 JSON 结构输出，明确字段名与类型；
2. **模板渲染**：服务端接收 JSON 后用预设模板渲染卡片，模型不直接控制排版；
3. **校验重试**：对 JSON 做结构校验，失败时触发一次重试；仍失败则降级为纯文本回答并标注"格式解析失败"。

**降级策略**：任一环节失败时，保证输出至少是**带出处的纯文本答案**，不出现"服务异常，请稍后再试"的空手而归。对应 [app/intelligence/rag.py](../app/intelligence/rag.py) 的 `_fallback_text`。

### 5. 双层知识库

| 机制 | 做法 |
| --- | --- |
| 物理隔离 | 两层文档分别入库，通过元数据字段 `layer` 区分 |
| 检索策略 | 官方层优先召回；官方层无结果时才检索经验层 |
| 冲突处理 | 两层结果冲突时，以官方层为准并提示差异 |
| 展示标注 | 经验层内容强提示"非官方，仅供参考" |
| 版本管理 | 文档更新时保留版本号，回答标注所依据的版本日期 |

| 层级 | 内容来源 | 标注方式 | 使用规则 |
| --- | --- | --- | --- |
| 官方层 | 校规校纪、职能部门通知、办事指南 | 标注文件名与发布日期 | 可直接作为回答依据 |
| 经验层 | 学长学姐实操经验、常见坑点 | 明确标注"非官方，仅供参考" | 仅作补充，不作为唯一依据 |

## 四、性能指标与优化

| 指标 | 目标值 | 优化手段 |
| --- | --- | --- |
| 平均响应时间 | ≤ 3 秒 | 高频问答缓存、流式输出 |
| 检索召回准确率 | ≥ 90%（Top-5 命中） | 混合检索 + 重排 |
| 出处标注率 | 100% | 由生成约束强制保证 |
| 卡片字段完整率 | ≥ 85% | 字段抽取校验 + 重试 |
| 并发承载 | ≥ 200 QPS | 异步框架 + 连接池 |
| 服务可用性 | ≥ 99% | 多模型备份切换、降级策略 |

**成本优化**：对高频重复问题（如"助学贷款怎么办"）建立结果缓存，命中缓存直接返回。

## 五、安全与隐私设计

| 维度 | 措施 |
| --- | --- |
| 数据最小化 | 不采集学号、姓名、身份证等任何个人信息 |
| 知识库合规 | 仅收录学校公开发布的规章制度与通知 |
| 日志匿名化 | 会话标识使用不可逆哈希，无法回溯到个人 |
| 传输安全 | 全链路 HTTPS/TLS 加密 |
| 内容标识 | AI 生成内容按规范作显著标识 |
| 敏感事项兜底 | 涉及资助资格、学籍异动等，明确提示以职能部门答复为准 |
| 权限控制 | 管理后台按角色分配权限，操作留痕 |
